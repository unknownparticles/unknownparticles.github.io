同时让几个 Agent 修问题、看代码、整理资料，很快就会遇到一个不属于“模型够不够聪明”的问题：我把新要求说在哪个窗口了？哪一个还在等我？刚才那次失败到底有没有恢复？如果这些关系全靠人记，开更多窗口也只是把管理工作一起放大。

读 DeepSeek Harness 团队的《Super-agent 设计探索：迈向更自主的 Agent 系统》，最有启发的地方，是它把这类问题放回了系统设计：把前台交互、具体执行、环境事件和长期状态分别组织好，让人把注意力留给决定与验收。

这篇是我的工程阅读笔记与独立实现练习，不是原文翻写。我们会沿着“一个图片导出问题如何从报告走到结果”这条线，观察几种职责怎样配合，再运行一个很小的教学模型。模型不接真实 AI，也不向 GitHub 或聊天平台发送消息，但会实际执行准入、去重、订阅、结果核对和上下文打包逻辑。

## 阅读依据：先把设计与实现分开

原文入口是[这篇微信公众号文章](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)。本次访问公众号正文触发了环境验证，因此通过[注明原作者的全文转载](https://www.chaincatcher.com/article/2300676)定位文章结构，再以 [DeepSeek 官方公开原型](https://github.com/deepseek-ai/dsh-superagent-prototype)的文档与源码核对工程行为。没有把转载网站当作 DeepSeek 官网。

下文涉及原型实现的链接固定在 `8c32a9d` 版本。官方 README 明确区分了研究原型、内部实现与文章中的未来方向，因此“文章提出了什么”和“公开代码已经做了什么”要分别看。本文新增的代次检查与字符预算模型是教学实现，也不冒充上游代码。

## 1. 一个问题，三种需要保存的连续性

假设有人在 Issue 里报告“导出 JPEG 后方向不对”，你让 Agent 复现。它正在检查元数据时，另一条讨论补充了一个新样本；与此同时，你又希望它检查网站在手机上的布局。两件工作可以分别执行，但不能让补充样本进入错误的任务。

这里至少有三种关系。第一种是对人的关系：用户希望有稳定的入口，能继续补充要求。第二种是对工作的关系：同一任务的输入、范围、进度和结果要能串起来。第三种是对运行实例的关系：现在究竟由哪一次执行负责这项工作。

会话窗口往往把它们揉在一起。关闭窗口似乎等于任务结束，换一台机器似乎就失去历史，重新启动又容易让旧任务重复执行。把这些关系拆开之后，才能说明哪些东西应该持久保存，哪些只是可以替换的运行过程。

原型的[领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/001-domain.md)把事件、讨论、工单与一次派工分别建模。对自己的系统不一定照搬全部名字，但“任务身份不等于执行器身份”这一点很值得保留：任务可以还在，负责它的某一次执行已经失败或结束了。

## 2. 把交互协调与具体执行分开

用户说“再检查一下竖图”，前台应该先找到相关任务，再让负责图片问题的执行器继续。它不必为了理解这句话，亲自接手整套图片解码、测试和修改过程。

![事件入口、全局协调、订阅直通与独立执行器的原创架构示意](/img/posts/superagent/architecture.svg)

这张图表达的是逻辑职责，不能拿它当完整部署拓扑。协调层维护跨任务关联，执行器保留具体任务的细节；实际进程、Session 和机器怎样分布，可以另外设计。

从工程角度看，最直接的好处是避免耗时操作堵住接收新输入的入口。如果图片测试要跑很久，可以先启动工作并记录身份，之后接收“先别改编码器”的补充；结果通过事件回来，再核对它属于哪个任务。这并不表示模型在推理的同一个瞬间可以任意中断，系统仍然要安排输入进入下一次可处理的边界。

公开原型的[执行文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/003-execution.md)说明了任务执行器、后台工作以及报告的组织方式。它给每个工单安排独立的执行会话与目录。需要注意：独立上下文和目录不能自动消除共享资源冲突；如果两项工作最终都要改同一个分支或外部服务，还需要合并、锁、串行化或其他冲突处理。

### 真正重要的是谁需要知道哪些细节

协调层知道“图片问题等待复现结果”，通常就够了；某个 JPEG 标签在文件中的偏移、一次测试的完整日志，可以留在具体任务里。把这些细节每次都抄进全局上下文，只会让下一次路由更难。

反过来，执行器应该得到足够清楚的范围和验收条件。只说“处理一下这个问题”，它可能不断扩大修改；明确“复现方向标记导致的导出错误，保留其他滤镜行为，给出样本回归”，就更容易判断后面的补充是否仍属于同一项工作。这是我在实现教学模型时保留任务身份、输入与执行代次的原因。

## 3. 让稳定规则先处理事件，再把难判断的部分交给模型

一条群聊消息进入系统，不代表应当启动工作。闲聊、重复投递、机器人回执和真正的修改请求，处理方式可以不同。来源是否启用、发信者是否在允许范围内、事件 ID 是否已经见过，这些确定的问题适合交给程序。

需要理解语义的部分才留给模型：这句话是否提出新任务、是否与现有问题相关、有没有超出当前范围。两者的边界很重要。程序过滤可以稳定地执行规则，却不能只靠“包含 bug 字样”就可靠理解所有消息；模型可以理解更复杂的表达，却不能凭一段消息文字修改系统授予的权限。

可以对照原型的[准入与授权文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/002-authorization.md)。它区分明确请求、推断候选与忽略，并提供只记录可能行动、暂不启动的观察模式。这比一接上消息就让系统到处开任务，更容易检查规则有没有造成噪声。

### 已知归属的后续消息，为什么还要重新全局判断

第一次请求已经建立了“这项工作关注 Issue 42”的关系。后来的样本和测试结果，可以通过订阅送给这个任务，不必每次再让全局协调层重新猜归属。教学模型的第一个场景就演示这件事：两项新工作产生两次协调决定，补充样本沿既有订阅直通，重复事件被去重。

**收到上下文不等于获得新权限。** 一个没有启动工作权限的人，仍可能在相关讨论中提供有用的失败样本；这不意味着他能让执行器顺手修改部署配置。公开原型也将订阅传递与任务授权分开。本文模型只存入补充文本，没有实现完整的范围研判，界面因此明确标为“仅增加上下文”。

还有一个容易忽略的点：讨论与任务不必严格一对一。同一项修复可能同时关联问题报告和代码评审，一个讨论也可能被多项任务关注。这里为了让演示看得清楚，只创建少量固定任务；实际关系应该由业务身份和显式关联维护，不能拿一条文本相似度当永久关联。

## 4. 上下文要有入口，也要有预算

“把相关历史全发给模型”很省开发时间，却会让上下文越长越难管理。另一方面，只给一个没有说明的 ID，又会迫使模型连续调用工具，甚至不知道该找什么。

更实用的中间做法是保留短内容、对象身份和关联入口。例如当前事件给出 `thread:42`；读取这个讨论后，得到任务 `task:fix-42`；再从任务找到产物与验证记录。每次获取的资料都能继续导航，不必在第一步就搬来整个工作历史。

![当前事件沿稳定 ID 关联到讨论、任务与产物的原创示意图](/img/posts/superagent/context.svg)

教学模型用三个固定对象演示这个过程。滑动预算后，先保留每个对象的引用关系，再把剩余空间留给片段。点击“读取完整资料”时，展开的是本地保存的原文对象，展示被留在预算之外的信息。它不是向量检索，也没有模型参与选择。

以下就是浏览器与 Node.js 实际调用的打包函数。预算以 JavaScript 字符串长度计数，不是模型 token 数；之所以这样写，是为了能清楚验证输出是否真的没有超过上限。

```javascript
function packContext(budget) {
  if (!Number.isInteger(budget) || budget < 120) throw new Error('预算至少 120 个字符');
  const refs = documents.map(doc => `${doc.id} -> ${doc.related}`).join('\n');
  let text = refs;
  const limit = budget - refs.length;
  let remaining = limit;
  for (const doc of documents) {
    const prefix = `\n${doc.id}: `;
    if (remaining <= prefix.length) break;
    const snippet = doc.text.slice(0, remaining-prefix.length);
    text += prefix + snippet;
    remaining -= prefix.length+snippet.length;
  }
  return { text, used: text.length, budget, references: documents.map(doc => doc.id) };
}
```

真实系统要补上模型对应的 token 估算、工具返回预算和权限检查。更重要的是，摘要不能覆盖原始事实：样本地址、验收条件、已批准范围以及仍未回答的问题，都需要能回到可追溯记录。把这些信息压成“问题已经处理”，虽然短，却可能丢掉最有用的约束。

原型的[架构文档](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/007-architecture.md)可以帮助继续定位领域状态与适配层；阅读时先追踪一个对象的读取路径，再看它带出了哪些关联信息，比先背下所有术语更容易理解。

## 5. 异步开始，只说明工作被接收了

用户请求修图后，系统立即回复“已开始”，改善的是交互反馈，不能把它当作已经修好。后面至少还要知道任务在哪里排队、谁在执行、执行结果怎样回来，以及结果是否经过检查。

假设执行器完成了测试，并把一个结果消息交给发送层。网络中断可能让发送失败，服务重启又可能重新读到同一个事件。这时“再试一次”很自然，但如果每次尝试都生成新结果身份，就可能给用户发出多份相同报告。

公开原型在[状态存储](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/store.ts)中记录消息回执，并在 [Outbox](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/app/outbox.ts)组织发送。理解这里的重点是：业务结果、等待发送与实际送达是不同的状态。本文模型只登记一条可审阅结果，根本没有真实发送动作。

### 不要轻易承诺只执行一次

一次修复可能同时涉及保存记录、提交代码、创建 PR 和通知聊天平台，很难靠一个布尔变量把这些外部动作变成同一笔事务。稳定 ID、幂等接口、发送回执与可重试的步骤，能减少重复并帮助恢复，但仍要说明边界。

例如本地结果已经登记，外部平台其实接收了消息，只是返回响应丢了。恢复时若仅检查“本地是否记作已发送”，仍然可能再次发送。是否能查询外部回执、复用相同幂等键，取决于实际平台。教学模型的“一次登记”不能推导为生产系统的端到端 exactly-once。

## 6. 重启以后，怎样识别迟到的旧结果

故障恢复里常见的危险不是没有结果，而是两份不同执行的结果都回来了。系统判断第一次执行没有进展，重新派了一次；旧执行器其实只是暂时断网，稍后也交回了报告。此时谁有资格改变任务状态？

下面的示意图与代码采用一个简单办法：任务每次恢复都增加执行代次，结果必须带着自己的代次。旧结果仍可记录为诊断信息，但不能直接覆盖当前状态。这个代次机制是本文的教学设计，不表示上游恰好使用同一套字段。

![重启后换发执行代次并拒绝迟到结果的原创示意图](/img/posts/superagent/recovery.svg)

```javascript
// 摘自可下载模型；完整文件包含状态定义、接收事件与执行入口。
class MiniRuntimeExcerpt {
complete(id, generation) {
    const task = this.state.tasks[id];
    if (!task || task.status !== 'running' || task.generation !== generation) {
      this.record('gate', `拒绝过期或重复结果 ${id}@${generation}`); return;
    }
    task.status = 'ready';
    const resultId = `result:${id}`;
    if (!this.state.outbox.some(result => result.id === resultId))
      this.state.outbox.push({ id: resultId, text: `${id} 的可审阅结果` });
    this.record('outbox', `${id}@${generation} 完成；结果登记一次，尚未对外发送`);
  }
recover(id) {
    const task = this.state.tasks[id];
    if (!task || task.status !== 'running') return;
    if (task.attempts >= 2) {
      task.status = 'needs-human';
      task.generation++; // 让旧执行器的结果也失效
      this.record('watchdog', `${id} 已到重试上限，转人工处理`); return;
    }
    task.attempts++; task.generation++;
    this.record('watchdog', `${id} 无进展；换发执行代次 ${task.generation}，旧代次失效`);
  }
}
```

代码里的 `recover()` 由演示脚本注入“无进展”信号后调用，不会自己判断真实模型有没有跑偏。恢复场景先序列化一份 JSON 快照，再用它创建新的运行时；之后换发代次，演示旧结果被拒绝、新结果登记一次，以及重复回调不再登记。

这还不是完整的生产级 fencing。它只保护模型内的结果更新，无法撤销旧执行器已经写出的文件或发出的请求。要保护共享存储或外部服务，接收写入的一方也要验证代次或采用其他并发控制。把过期结果拦住，是恢复路径中的一环，不是所有副作用都已经解决。

### Watchdog 要看进展，而不只是看进程是否活着

进程还在、心跳正常，也可能一直重复相同的无效尝试。因此外部观察者需要看更有意义的事实：是否产生新验证记录、是否被同一个错误反复阻塞、有没有明确等待人的决定。日志变长不能自动算作有进展。

对于本文的小模型，第二次恢复请求会触发重试上限并转人工。实际系统还要区别临时网络问题、明确失败和等待回答：等待人工决定时反复重启，只会丢失上下文并增加成本。原型的执行文档也将任务报告、人工注意项与重试分别处理。

## 7. 状态可以恢复，执行环境却不能凭空重建

JSON 快照可以说明任务做到了哪一步，却不包含复现图片、未提交修改、系统工具链或一台设备上的内网服务。任务状态和执行环境各自有生命周期，不能把“会话历史还在”理解成“换台机器就能无缝继续”。

可以继续沿图片问题想下去：协调过程运行在服务器上，实际复现需要开发机里的一张样本和本地编码器。开发机离线时，服务器仍能接收补充，但需要标记执行环境不可用；等设备恢复后，核对环境身份与任务版本，再决定继续、重建或请求帮助。这是架构层的设计方向，本文没有实现远程执行，也不据此宣称公开原型已提供完整的跨设备能力。

另一种情况是 Worker 重启了，代码目录还在。此时应先确认上次留下的修改、正在运行的命令和产物，不能看到一次派工结束就立刻重做所有步骤。对自己维护的工具，明确保存任务记录、代码工作区和外部服务状态分别由谁负责，会比把它们笼统称作“记忆”更便于恢复。

### 提前准备，可以从不产生外部影响的工作开始

持续收到事件之后，系统有机会先准备资料：整理失败样本、检查已有测试、生成一份待审阅草稿。是否允许这样做，应由明确的规则、费用范围和工作区约束决定，不能因为事件“看起来有价值”就顺手改变线上环境。

可以先只记录“这条规则原本会触发什么”，再由维护者检查命中结果。准备有价值的结果与发布结果，也是两个不同的决定。本文没有接入自动执行，只用固定事件验证路由和状态；这给以后接入真实执行器留出了清楚的边界。

## 8. 把“人的注意力”放进输出设计

一个后台任务不需要把每次工具调用都发进群里。用户更需要的是现在能用的结果、一个具体待决定的问题，或者明确的阻塞说明。原型的[设计原则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/docs/000-philosophy.md)也从这种注意力成本出发组织交互。

以图片方向修复为例，最后的交付可以是“已复现方向标记 6 导致的错误，修改导出流程，新增回归样本，PR 待审阅”，并附详细记录。比起在群里连续发布读了哪个文件、又启动了什么命令，这种输出更容易让人判断下一步要做什么。

通知安静不等于内部不可观察。任务状态、失败原因、验证日志应该能按需查看；只是不要把全部细节当作必须立即打断用户的消息。在真正上线前，可以观察一段时间：哪些候选工作实际有价值，哪些通知让用户采取了行动，哪些只是制造重复确认。

## 9. 运行本文的小模型

这是一个无第三方依赖的 ES module。下载后使用支持 ES module 的 Node.js 执行：

```bash
node superagent-runtime.mjs
```

命令会打印两个场景的逐步日志，再输出 180 字符预算下的打包结果。在本站仓库中，还可以运行回归检查：

```bash
npm run test:superagent
```

检查会核对准入与重复事件、两项独立工作、订阅直通、JSON 快照恢复、旧代次拒绝、重试上限与结果唯一登记，还会遍历 120～600 的每一种整数预算，确认引用保留且输出不超上限。文章展示的关键函数也与下载文件进行一致性比对。

这里的“执行器”只是状态记录，并没有后台模型、真实并行命令或持久数据库。教学模型的作用，是把状态变化做成可以运行和检查的具体对象。要继续接真实系统，可以先给运行时实现存储与执行器接口，再补上租约、投递回执、权限重验、费用预算与人工入口，逐项验证失败路径。

## 最值得带走的设计习惯

对我来说，这次阅读最大的收获是改变了提问方式：除了“模型能不能解决这个任务”，还要问“下一条消息怎样找到这个任务”“进程换了以后还能不能知道做到哪里”“结果回来时有没有资格继续写入”。这些问题一旦有了明确答案，跨会话协作才有机会稳定下来。

自己的工具不必从一开始就长成复杂平台。先给事件和任务稳定身份，把相关上下文送到正确位置，留下足够恢复的记录，再决定何时需要全局协调和外部观察。下面的交互实验可以作为起点：每走一步，都检查状态、引用和结果有没有与预期对应。
