## 前言

一个页面从“能显示”到“能交给别人用”，中间还有不少事情：按钮点击以后状态怎样变化，请求失败时显示什么，刷新深层地址还能不能打开，构建产物又是怎样送到服务器上的。单看框架名字，很难理解这些环节为什么需要放在一起。

这篇文章把常见前端代码放回这条工作流程里看。React 和 Vue 用来说明状态与渲染，构建配置负责把源码变成浏览器能加载的产物，请求、路由和部署则决定页面离开开发服务器以后能否正常工作。读的时候可以先选一套框架，不必把所有例子都装进同一个项目。

### 2. 框架选择

目前主流的前端框架有：

#### React
```jsx
// React 函数组件示例
import React, { useState } from 'react';

function Counter() {
    const [count, setCount] = useState(0);
    
    return (
        <div>
            <p>Count: {count}</p>
            <button onClick={() => setCount(value => value + 1)}>
                Increment
            </button>
        </div>
    );
}
```

#### Vue.js
```vue
<!-- Vue 3 Composition API -->
<template>
    <div>
        <p>Count: {{ count }}</p>
        <button @click="increment">Increment</button>
    </div>
</template>

<script>
import { ref } from 'vue';

export default {
    setup() {
        const count = ref(0);
        
        const increment = () => {
            count.value++;
        };
        
        return {
            count,
            increment
        };
    }
};
</script>
```

### 开发服务器跑通以后，还要检查什么

开发时能打开页面，只说明开发服务器提供了需要的转换与资源。发布时浏览器加载的是构建目录里的文件，入口路径、资源前缀和宿主返回的内容都可能发生变化。因此每次调整构建配置后，应该实际生成一次产物，再用预览或静态服务器访问，而不是只看终端里有没有红字。

配置也不宜按“选项越多越专业”的思路叠加。先弄清入口在哪里、哪些文件需要转换、输出到哪里，再按需求加入插件。出了问题时，知道每条配置在解决什么，才能判断该改源码、构建还是托管设置。

## 状态管理

### 1. React 状态管理

#### Redux Toolkit

新代码使用 Redux Toolkit；以下 store 仍需通过 React-Redux Provider 接入组件。
```javascript
// store.js
import { configureStore, createSlice } from '@reduxjs/toolkit';

const counter = createSlice({
    name: 'counter',
    initialState: { count: 0 },
    reducers: {
        increment(state) { state.count += 1; }
    }
});
export const { increment } = counter.actions;
export const store = configureStore({ reducer: { counter: counter.reducer } });
```

#### Context API
```jsx
// UserContext.js
import React, { createContext, useContext, useState } from 'react';

const UserContext = createContext();

export function useUser() {
    return useContext(UserContext);
}

export function UserProvider({ children }) {
    const [user, setUser] = useState(null);
    
    return (
        <UserContext.Provider value={{ user, setUser }}>
            {children}
        </UserContext.Provider>
    );
}
```

### 2. Vue 状态管理

#### Pinia (Vue 3)
```javascript
// stores/user.js
import { defineStore } from 'pinia';

export const useUserStore = defineStore('user', {
    state: () => ({
        user: null,
        isLoggedIn: false
    }),
    actions: {
        setUser(userData) {
            this.user = userData;
            this.isLoggedIn = true;
        },
        logout() {
            this.user = null;
            this.isLoggedIn = false;
        }
    }
});
```

### 状态应该放在哪里

可以从一个表单出发判断。只有输入框自己用的临时内容，留在组件附近就足够；同一页面的兄弟组件都需要读写时，再把状态提升到共同的上层。登录用户、跨页面草稿这类长期共享的信息，才更值得讨论全局存储。

是否全局共享，与是否需要持久化又是两回事。放进 store 的数据，刷新页面后也可能消失；写进 localStorage 的数据，又需要考虑失效、版本变化和主动清除。把“谁需要用”和“需要保存多久”分开问，往往就能缩小工具选择范围。

上面的计数器适合演示更新机制，却不能代表真实业务的全部状态。一次请求还会经历等待、成功、失败等阶段；如果只有一个 data 字段而没有状态区分，空白界面既可能表示没数据，也可能表示请求还没完成，用户就不知道该等待还是重试。

## 路由管理

### React Router

使用 history 路由的 SPA 需要宿主把未知应用路径回退到入口 HTML；纯静态托管没有这个能力时，可考虑 hash 路由。
```jsx
// App.js
import { BrowserRouter, Routes, Route } from 'react-router-dom';
import Home from './pages/Home';
import About from './pages/About';

function App() {
    return (
        <BrowserRouter>
            <Routes>
                <Route path="/" element={<Home />} />
                <Route path="/about" element={<About />} />
            </Routes>
        </BrowserRouter>
    );
}
```

### Vue Router
```javascript
// router/index.js
import { createRouter, createWebHistory } from 'vue-router';
import Home from '../views/Home.vue';

const routes = [
    { path: '/', component: Home },
    { path: '/about', component: About }
];

export const router = createRouter({
    history: createWebHistory(),
    routes
});
```

## API 交互

### 1. Fetch API

Fetch 遇到 HTTP 404／500 不会自动 reject；必须检查 `response.ok`。此例把错误继续抛给调用方，由界面呈现错误与重试状态。
```javascript
// 使用 Fetch API
async function fetchData() {
    try {
        const response = await fetch('/api/data');
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const data = await response.json();
        return data;
    } catch (error) {
        console.error('Error:', error);
        throw error;
    }
}
```

### 2. Axios
```javascript
// 使用 Axios
import axios from 'axios';

const api = axios.create({
    baseURL: 'https://api.example.com',
    timeout: 10000
});

// 请求拦截器
api.interceptors.request.use(config => {
    // 添加认证 token
    const token = localStorage.getItem('token');
    if (token) {
        config.headers.Authorization = `Bearer ${token}`;
    }
    return config;
});
```

### 把错误交回到能处理它的地方

请求函数负责说明成功拿到了什么，或者为什么失败；界面负责把这个结果变成用户能理解的反馈。上面的 Fetch 示例在记录错误后继续抛出，就是为了让调用方有机会停止加载、保留旧数据、显示重试按钮。

还要考虑请求之间的关系。用户快速切换两次筛选条件，第一次请求可能比第二次更晚返回。如果不区分它们，界面就会被旧结果覆盖。可以在调用层跟踪当前请求，或使用取消机制；具体选择取决于业务，但“后来返回”不等于“用户最后想看的结果”。

## 性能优化

### 1. 代码分割
```jsx
// React 代码分割
import { lazy, Suspense } from 'react';

const LazyComponent = lazy(() => import('./LazyComponent'));

function App() {
    return (
        <Suspense fallback={<div>Loading...</div>}>
            <LazyComponent />
        </Suspense>
    );
}
```

### 2. 图片优化
```html
<!-- 响应式图片 -->
<img 
    src="image-small.jpg" 
    srcset="image-medium.jpg 1000w, image-large.jpg 2000w"
    sizes="(max-width: 600px) 100vw, 50vw"
    alt="Optimized image"
>

<!-- WebP 格式 -->
<picture>
    <source srcset="image.webp" type="image/webp">
    <img src="image.jpg" alt="Fallback image">
</picture>
```

### 3. 缓存策略

以下只演示安装期预缓存，尚未实现 `fetch` 读取缓存、旧缓存清理与更新策略，因此不能单凭此段声称离线可用。资源路径必须换成真实构建产物；带哈希的文件名不宜手写。
```javascript
// Service Worker 缓存
const CACHE_NAME = 'my-app-cache-v1';
const urlsToCache = [
    '/',
    '/static/js/bundle.js',
    '/static/css/main.css'
];

self.addEventListener('install', event => {
    event.waitUntil(
        caches.open(CACHE_NAME)
            .then(cache => cache.addAll(urlsToCache))
    );
});
```

### 优化要对应用户能感受到的等待

代码分割主要推迟暂时用不到的代码；图片优化主要减少下载和解码成本；缓存则尝试复用已经拿到的资源。它们解决的不是同一个问题，不能把几项配置加上就认为性能已经完成。

例如首页图片很大，但点击详情后才用到的编辑器代码也进入了首页包，可以分别检查首屏图片尺寸和代码加载时机。反过来，如果卡顿发生在输入过程中，继续压缩图片未必有帮助，应该观察交互触发了哪些计算和渲染。先复现用户等待的那一步，再选择对应手段。

## 部署策略

### 1. 静态网站托管
静态站点需要把构建产物交给部署任务，不能假设前一任务的工作目录自动共享。可使用本站的 [部署工作流](https://github.com/unknownparticles/unknownparticles.github.io/blob/master/.github/workflows/deploy.yml)作为具体项目示例，或参考下一篇 [开源项目实践](/2025/11/11/开源项目实践/)中的完整 Pages 构建与部署配置。

项目的 Node.js 版本应与 `engines` 和锁文件匹配；不要复制已结束维护的 Node 16 环境。Actions 的触发分支也要与实际仓库一致，本站是 `master`。

### 2. Docker 部署
```dockerfile
# 面向产出 dist/ 的纯静态前端，假设仓库已有 package-lock.json。
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:stable-alpine
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
```

构建上下文应通过 `.dockerignore` 排除 `node_modules`、`dist`、`.git` 与本地秘密文件。上述 Nginx 示例适用于静态文件，history 路由 SPA 需额外配置 fallback，SSR 服务需使用对应服务端产物。

## 结语

可以用一个小页面把本文串起来：加载一份数据，区分等待与错误，让用户切换内容，再构建并部署到实际托管环境。每一步都有可观察的结果，也能看出框架、状态、请求和部署各自负责什么。

等这条路径稳定以后，再加入代码分割、缓存或更复杂的状态管理。这样每项工具都有明确用途，遇到问题时也知道应该先检查哪一层。
